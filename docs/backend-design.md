# 后端设计：分工、状态与判断证据

## 目标与技术边界

后端负责三件最关键的事：在自动化前给出可解释的逐步骤分工建议；保证新人首次判断前无法取得 AI 结论；保存首次判断、提示、修订和主管审核，并据此提出下一任务的支持建议。

MVP 可采用 Node.js API、SQLite 和服务端模型调用。API Key 仅保存在服务端。演示材料应脱敏或标注为模拟数据；真实客户数据接入须另行设计权限、隐私与合规处理。

## 任务状态机

```text
draft
  → proposed
  → assigned
  → in_progress
  → first_submitted
  → revision_in_progress
  → pending_review
  → approved
                 ↘ changes_requested → revision_in_progress
```

`proposed` 表示系统给出建议；`assigned` 表示主管已经确认。`first_submitted` 是不可回退的关键节点：首次判断保存后才允许生成或访问针对该判断的 AI 证据检查。退回修改只新增版本，不覆盖首次版。状态转换需记录操作者和时间。

## 分工决策逻辑

系统先拆分任务步骤，再按以下顺序判断：

1. **硬约束：** 访问权限、数据边界、截止时间、是否有合适审核人、是否要求特定角色批准。违反硬约束时，不推荐新人执行该步骤。
2. **学习价值：** 步骤是否直接对应企业定义的目标能力；员工是否有能力缺口且具备尝试基础；该步骤是否包含真实判断和新情境经验。
3. **业务代价：** 错误影响、可逆性、时间压力、对流程的阻塞、监督和返工成本，以及 AI 自动化收益。

每步输出 `reserve_for_learner`、`automate_with_ai` 或 `senior_led`，并附可读理由、命中的规则和审核要求。主管可以改判并记录原因。MVP 可用透明规则和少量阈值；不要让模型直接决定权限或最终业务责任。

示例：反馈去重可建议 AI 执行；问题模式与调查优先级因匹配“用户洞察”能力缺口而预留给新人；批准产品结论由主管负责。整理后的反馈必须保留原文 ID 与映射，避免 AI 合并不同问题后抹去学习证据。

## AI 内容访问控制

- 服务端按角色和任务状态提供不同响应。新人首次提交前的读取接口只返回材料、背景和允许的提示，不返回 AI 分类、排序、结论或内部参考答案。
- 前端不能通过隐藏组件实现这一限制；相关内容不得预取或放入同一响应的隐藏字段。
- 提交首次判断时，后端在事务中保存不可覆盖的版本、证据引用、提示使用情况和提交时间，再推进状态。
- 首次提交后，服务端可以调用模型检查证据并生成分级反馈。模型输出仅作提示，不能代替主管批准。
- 每次提示请求都检查允许的级别和任务状态，保存提示内容、级别、时间与模型版本。模型生成的提交前提示应限制为问题或线索，避免直接泄露结论。

## 核心数据模型

| 表 / 实体 | 关键内容 |
| --- | --- |
| `users` | 用户 ID、角色、所属团队；MVP 可使用固定演示账号，但 API 仍检查角色 |
| `capabilities`、`learner_capabilities` | 企业定义的能力与员工当前发展重点；保留证据来源 |
| `tasks` | 来源、标题、截止时间、风险、审核人、材料来源、状态 |
| `feedback_items` | 原始反馈 ID、脱敏文本、来源标记；整理结果保留原文映射 |
| `task_steps`、`allocations` | 步骤、系统建议、理由、主管确认分工和改判原因 |
| `judgment_versions` | 首次判断及每次修订、结构化结论、证据引用、修改理由 |
| `hint_events` | 提示级别、内容、请求人、时间、模型版本 |
| `reviews` | 主管反馈、审核结果、审核时间、业务结论状态 |
| `capability_evidence` | 本次表现、帮助程度、下一次支持建议及主管确认 |
| `audit_events` | 状态变化、分工确认、提交、提示和审核等关键操作 |

首次判断和审计事件采用追加记录。后续版本通过 `version_number` 和 `parent_version_id` 关联，不能更新或删除原始提交。

## API 草案

| 方法与路径 | 用途 | 主要约束 |
| --- | --- | --- |
| `POST /tasks` | 主管新建任务 | 校验材料访问范围和审核人 |
| `POST /tasks/:id/proposal` | 生成逐步骤分工建议 | 返回规则理由与风险标记 |
| `POST /tasks/:id/assignment` | 主管确认或改判 | 保存决定及改判原因 |
| `GET /tasks/:id` | 读取角色对应的任务视图 | 按角色和状态裁剪字段 |
| `POST /tasks/:id/first-judgment` | 新人提交首次判断 | 只允许一次；保存证据与提示记录 |
| `POST /tasks/:id/hints` | 请求下一层提示 | 检查状态、级别和泄露限制 |
| `POST /tasks/:id/revisions` | 新人提交修订 | 新增版本，不覆盖首次版 |
| `POST /tasks/:id/review` | 主管批准或退回 | 保存审核与业务状态 |
| `GET /tasks/:id/history` | 查看判断和审核轨迹 | 新人与主管按权限读取 |

提交接口需要校验当前状态与版本号，避免重复点击或并发请求创建两个“首次判断”。所有写操作记录操作者；角色切换的演示界面不能成为绕过服务端权限的方式。

## 审核后的能力更新

主管审核产生一条能力证据，包含判断质量、遗漏、帮助程度和情境难度。系统据此给出下一任务的提示建议：减少、保持或增加。建议必须显示依据，并允许主管确认或修改。单次任务不能自动将能力标记为“已掌握”；掌握需要在相似但不同的真实任务中再次验证。

## 验证顺序

1. 状态机和数据库记录能完整跑通“主管确认 → 首次判断 → 修订 → 审核”。
2. 在首次提交前，以新人身份直接请求各读取接口，确认响应中没有 AI 结论；提交后确认首次版不可覆盖。
3. 检查原始反馈、整理映射、提示和修订均能从主管审核页读取。
4. 审核后生成有理由的下次支持建议，但不自动宣布能力掌握。
