# Demo 后端分步开发计划

## 1. 目标、依据与范围

本计划对应 [User Story](../../docs/user-story.md)、[前端设计](../../docs/frontend-design.md)、[后端设计](../../docs/backend-design.md)，并以 [产品架构图 01](../../product%20design/01-apprenticeship-architecture.svg)、[分工与权限图 02](../../product%20design/02-work-allocation-and-authority.svg)、[真实任务闭环图 03](../../product%20design/03-real-work-learning-loop.svg) 和 [首项任务入口图 04](../../product%20design/04-first-real-task-entry.svg) 为流程约束。

Day 3 Demo 只覆盖**一个企业定义的能力、一项有明确来源的工作、一名新人、一位主管**。示例能力是“用户洞察”，工作是分析商户开户与验证流程反馈，提出两个优先调查的问题并引用原文。若演示材料为模拟数据，须在任务记录和界面中明确标记；不能把模拟反馈称为真实客户数据。跨团队匹配、自动生成训练任务、长期职业规划与自动认证能力均不在本轮范围内。

后端必须证明三件事：

1. 在自动化前，依据透明规则逐步骤提出**学习安排**与**执行权限**，由主管确认或改判。
2. 新人首次判断保存前，任何面向新人的 API 响应都不包含 AI 的分类、排序、最终结论或内部参考答案。
3. 首次判断、提示、修订、主管业务审核和能力证据均可追溯；本次业务批准不等于能力掌握。

计划使用 Node.js API、SQLite 和服务端模型调用。按当前 [README](../../README.md) 的选型，Demo 的模型候选为 `gpt-4o-mini`；模型负责材料整理、有限提示和提交后证据检查，**不决定角色权限、硬约束、最终分工或业务批准**。API Key 仅保存在服务端。企业阶段再评估本地 Ollama 与 `gemma3:12b`，不作为 Day 3 的依赖。

## 2. 演示前需收集的资料

按以下顺序准备，先确定业务标准，再制作种子数据和规则。业务负责人须审阅任务材料和答案边界。

| 顺序 | 资料 | 最低要求与用途 |
| --- | --- | --- |
| 1 | 工作项与来源 | 任务标题、来源记录、业务目标、截止时间、风险、可逆性、审核人和最终结论的使用范围。若只是模拟流程，应如实标记，不能声称已在真实工作中验证。 |
| 2 | 能力目标与起点 | 企业定义“用户洞察”的可观察行为；用招聘评估、既有任务或主管观察说明新人当前的能力缺口和尝试基础，不伪造精确能力分数。 |
| 3 | 反馈材料 | 可使用的脱敏原文或明确标记的模拟文本；每条有稳定 ID、流程阶段、来源标记。覆盖重复反馈、不同阶段、相互矛盾和可能遗漏的线索。至少包含 UI 示例使用的 `FB-014`、`FB-018`、`FB-021`、`FB-024`、`FB-027`、`FB-036`。 |
| 4 | 整理映射 | 每个去重组或摘要能追溯到全部原文 ID；不得把不同问题合并后丢失原始证据。 |
| 5 | 主管评审标准 | 两个优先问题的判定依据、可接受的证据质量、关键矛盾或不确定性、退回修改条件，以及验证／风控规则变更需要的独立审批。评审参考材料不得进入新人首次提交前的读取响应。 |
| 6 | 后续验证材料 | 一个相似能力、不同情境的任务样本，用来说明下一轮如何检验更少帮助下的表现；Day 3 不需要把第二轮完整开发出来。 |

## 3. 分步开发与验收

每一步完成后保留一个可运行的 API 演示路径。四个前端页面依次对应主管分工、首次判断、提示与修订、主管审核；无需先建设复杂仪表盘。

| 步骤 | 实现内容 | 完成判据 |
| --- | --- | --- |
| 0. 固定演示契约 | 录入一项任务、一个能力、两个固定演示角色；确定字段名、反馈 ID、材料来源标记和主管评审标准。 | 团队能用同一份样本解释工作来源、能力目标、审核人和权限边界。 |
| 1. 状态机与持久化 | 建立任务、步骤、分工、反馈、版本、提示、审核、能力证据和审计记录；写操作记录操作者与时间。 | 合法状态可推进；非法转换被拒绝；刷新后数据仍在。 |
| 2. 透明分工规则 | 先检查访问权限、数据范围、截止时间、风险和审核能力；再判断能力关联、员工准备度、练习价值、业务代价与自动化收益。逐步骤输出建议、命中规则、理由和审批要求。 | 去重建议 AI 处理，模式识别和优先级判断建议预留新人，业务使用由主管批准；主管可改判并留原因，但不能绕过硬约束。 |
| 3. 首次判断保护 | 任务读取按角色和状态裁剪；首次提交校验证据 ID、当前状态和版本，并在数据库事务中追加不可覆盖的版本。 | 用新人身份直接请求全部读取接口，首次提交前均拿不到 AI 结论；重复点击或并发请求只产生一个首次版。 |
| 4. 有限提示与模型接口 | 实现服务端模型适配层、输出结构校验、来源 ID 校验和提示事件记录；模型不可访问审批写入路径。 | 提交前只有受控的问题式提示；提交后才开放具体线索和证据检查。每次帮助留下级别、内容、时间、请求人和模型版本。 |
| 5. 修订、审核与能力证据 | 修订只新增版本并要求说明改变原因；主管查看原文、映射、首次版、提示和修订，批准或退回业务输出，另行确认下一任务支持程度。 | 退回后原版本仍可查看；业务批准与能力证据分别保存；系统不凭一次任务自动标记“已掌握”。 |
| 6. 四页联调与演示 | 将现有四张 UI 对应的页面连接 API，准备正常流程与失败场景脚本。 | 从主管确认到审核完整跑通；网络响应和数据库记录均能展示关键约束确实由后端执行。 |

### 状态与接口以现有后端规范为准

沿用 `draft → proposed → assigned → in_progress → first_submitted → revision_in_progress → pending_review → approved`，主管退回时进入 `changes_requested`，再次修订不覆盖旧版本。`first_submitted` 是不可回退的关键节点。

优先实现 [后端设计](../../docs/backend-design.md) 已列出的 `POST /tasks`、`POST /tasks/:id/proposal`、`POST /tasks/:id/assignment`、`GET /tasks/:id`、`POST /tasks/:id/first-judgment`、`POST /tasks/:id/hints`、`POST /tasks/:id/revisions`、`POST /tasks/:id/review` 和 `GET /tasks/:id/history`。不为 Demo 另造平行流程或多任务推荐 API。

### 三级帮助的时序

1. **一级反思问题：** 首次提交前允许按需请求，只问应比较什么，不给问题分类或优先级；如使用，首次判断须标记为“有提示”。
2. **二级具体线索：** MVP 在首次版保存后开放，指出值得重看的反馈范围，不给最终答案。
3. **三级提交后证据检查：** 首次版保存后才调用／展示，指出可能遗漏、矛盾证据和待核实假设。

该时序同时满足产品流程图 03 的“首次提交前可有有限问题，但提交后才进行 AI 证据检查”和前端规范的三级帮助。整理材料可在提交前发生，但摘要、映射或接口隐藏字段都不得泄露 AI 对问题的最终判断。模型输出必须经过服务端校验；它不能代替主管的业务审核。

## 4. 评估与验收资料

### 产品效果：分别记录交付和能力证据

请主管在开发前约定简短评审量表，至少检查：问题分组能否追溯原文、两个调查重点的理由是否充分、是否处理矛盾与不确定证据、需要何种帮助、审核耗时。记录判断质量与修订质量，但**不能仅凭提示次数或一次评分宣布能力掌握**。下一任务支持建议应有理由，允许主管减少、保持或增加提示，并在不同情境继续验证。

### 技术门槛：必须做的检查

1. 权限不足、无审核人或超出数据访问范围时，分工建议不能把关键步骤交给新人；主管改判也不能覆盖硬约束。
2. 首次提交前，检查新人所有可调用读取接口、提示接口和网络响应，确认没有 AI 分类、排序、结论或参考答案。
3. 首次提交只能成功一次；首次版、提示和审计事件不能被普通更新覆盖；修订只能新增版本。
4. AI 整理组与引用的反馈 ID 均能打开原文；模型生成的无效 ID 被拒绝或标注待核实。
5. 主管审核页能重建“分工确认 → 首次判断 → 帮助 → 修订 → 审核”的时间线。
6. 审核后的业务状态、能力证据和下一次支持建议分别可读；没有自动认证结果。

### 比赛演示证据

用一次端到端操作对应出题目标：新人亲自经历关键判断，AI 仍处理可自动化步骤；主管确认风险边界并提供真实反馈。准备一段直接调用接口的演示，证明“首次判断前锁定 AI 结论”和“首次版不可覆盖”不是静态图效果。当前提供的评判权重为 Potential Effectiveness 40%、Technical Feasibility 30%、Viability 10%、Originality 15%，合计 **95%**；正式提交前核对赛事原始评分表是否另有项目或修订。

## 5. 所需能力与三天迭代

| 能力 | 对应工作 |
| --- | --- |
| 产品／业务评审 | 定义目标能力、真实任务标准、审核人、风险边界和能力证据量表。 |
| Node.js／TypeScript 与 SQLite | API、状态机、事务、版本追加、角色权限和审计记录。 |
| AI 集成与评测 | 服务端调用、结构化输出校验、提示泄露检查、反馈 ID 验证和样本评测。 |
| 数据处理 | 脱敏、模拟标记、原文保留及去重映射。 |
| 前后端联调 | 四页接口契约、端到端路径和越权／重复提交失败场景。 |

- **Day 1：** 收集并确认任务材料与主管标准；完成种子数据、状态机和逐步骤分工规则。
- **Day 2：** 完成角色读取、首次判断事务、引用校验和提示记录；先通过泄露测试，再连接模型。
- **Day 3：** 完成提交后证据检查、修订、主管审核与四页联调；按固定脚本展示完整闭环并记录未实现的企业集成事项。

每轮先跑通一个垂直切片，再根据主管和新人试用反馈调整。若时间不足，优先保证**可解释的分工、服务端首次判断锁定、完整审核轨迹**；模型生成内容可以缩小范围，但不能用前端展示替代上述后端约束。
